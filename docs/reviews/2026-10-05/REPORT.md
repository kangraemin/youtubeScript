# 웹사이트 UX · 요약 품질 재검토 (2026-10-05)

대상: https://web-green-kappa-79.vercel.app (web/, Next.js) · prompts/summary-guidelines.md (13섹션 v2 스키마)
근거 파일: 이 디렉터리의 `shots/`(실렌더 스샷), `shoot.py`(측정 스크립트), `codex-ux-prompt.txt`·`codex-ux-consult.txt`(Codex 프롬프트·응답 원문), `sample110.json`(채널별 10건 표본), `reviewer-A-6channels.md`·`reviewer-B-5channels.md`(정성 검토 원문), `audit.md`(독립 감사 결과와 반영 내역), `v3/`(새 스키마 초안 + 재작성 2건 + 현행 요약 원본)

## 결론 먼저

1. **웹: 원인은 색·간격이 아니라 정보 순서·노출량·탐색 구조다.** 모바일 첫 화면에 요약이 0건이고, 상세 페이지는 모바일 16.2화면이며 결론이 아래에 있다. **처방은 (a) 점진 개선을 먼저 내고 효과를 잰 뒤 (b) 전면 재설계 여부를 정하는 것이다.** 처음 초안은 "(b)가 낫다"였지만 독립 감사에서 근거가 깨졌다.
   - 인용 접기 하나만으로 모바일 상세가 16.2화면에서 9.7화면으로 준다(감사 실측). (a)가 생각보다 크게 효과 있다.
   - Codex는 "데이터·API는 재사용하고 화면을 재설계"를 권했다. 스키마 교체까지 지지한 것은 아니다.
   - 다만 홈 정보구조(채널 통계 먼저, 필터 부재)는 (a)로 고쳐도 구조가 그대로다. v3 스키마를 도입하면 상세 화면은 어차피 새로 써야 한다. 그래서 (b)는 v3 파일럿 결과와 묶어서 판단하는 것이 맞다.
2. **요약: 13섹션 스키마는 최선이 아니다.** 같은 발언이 섹션만 바꿔 4~7번 반복된다. 표본 110건에서 인용의 29%가 다른 항목에도 들어간 중복 인용이다. buys·sells는 87%·90%가 비어 있고, 채워진 것도 절반이 실제 매매가 아니다. 교양·숏폼에도 주식 섹션을 억지로 채운다.
   - 요약이 원문보다 긴 경우가 많다. 텍스트만 비교하면 중앙값 1.14배, 110건 중 65건이 원문보다 길다.
   - 인용 자체는 대부분 원문과 일치한다(불일치율은 채널별 0.1~5%).
   - 현행 가이드의 분량 상한·중복 병합 규칙조차 지켜지지 않는다(감사 근사 85/110 초과).
3. 두 문제는 연결돼 있다. 스키마와 가이드가 "무손실 추출"을 목표로 하니 화면도 추출물을 그대로 쏟아낸다. **v3 스키마(독자 우선)는 파일럿 N건을 운영 파이프라인으로 돌려 재현성을 확인한 뒤 전환을 결정하라.** 재작성 2건은 이 세션 모델이 손으로 쓴 것이라 그 자체로는 근거가 부족하다.

## 과제 1 — 웹사이트

### 측정 방법
Playwright(Chromium)로 라이브 사이트를 렌더했다. PC는 1440×900, 모바일은 390×844(DPR 2, is_mobile)이다. 홈, 검색("엔비디아"), 첫 영상 상세(`/video/wQwoW_HgNnM`), 첫 채널(`/channel/shukaworld`)을 찍었다. 스크립트는 `shoot.py`에 있다.

| 지표 | PC | 모바일 |
|---|---|---|
| 홈 전체 높이 (카드 20개) | 2,476px = 2.8화면 | 8,662px = **10.3화면** |
| 첫 영상 카드 y | 646 (첫 화면 안) | **1,222 (첫 화면 밖)** |
| 검색창 y | 536 | **1,112 (첫 화면 밖)** |
| 상세 페이지 높이 | 9.8화면 | **16.2화면** |
| 상세 페이지 인용·타임스탬프 링크 | 101개 | 101개 |
| 홈 글자 노드 중 12px 미만 | 106/189 | 106/189 |
| 가로 스크롤 | 없음 | 없음 |

### 진단 (스샷 근거)

**① 첫 화면 진입: 모바일 첫 화면이 채널 통계로만 채워진다** (`shots/mo_home_fold.png`)
- 첫 화면에는 채널 요약 편수 카드 10장(239, 315, 498…, 11번째는 화면 밖)이 보인다. 제품의 본체인 요약은 한 건도 안 보인다. 검색창도 1.3화면을 내려가야 나온다.
- 편수는 운영자에게 필요한 지표다. 독자는 "오늘 뭐가 중요한가"를 먼저 알고 싶어 한다.
- 코드: `web/app/page.tsx:82-111`. 채널 섹션이 피드보다 먼저 나온다.

**② 정보구조: 상세 페이지가 결론보다 분류를 먼저 보여준다** (`shots/pc_video_fold.png`, `shots/mo_video_fold.png`, `shots/pc_video_overview.png`)
- PC 첫 화면의 약 절반(472/900px)을 hq 썸네일이 차지한다(모바일은 196/844px). 그 아래에 제목, 헤드라인(부제)이 나오고, **같은 헤드라인이 "HEADLINE" 박스로 한 번 더** 나온다(`web/app/video/[vid]/page.tsx:77-78`, `web/components/SummaryCard.tsx:17-24`).
- 코드상 섹션 순서는 매수 → 매도 → 봐야 할 것 → 용어 → 거시 → 차트 → 결론 → 영상 흐름 → 학습 → 숫자 → 실행이다(`SummaryCard.tsx:26-159`). 결론과 흐름이 7·8번째다. 매수·매도는 비면 그리지 않으므로 측정한 영상에선 5·6번째다. 용어 설명은 거시 진단보다 앞에 있다.
- **3~5문장짜리 `raw_summary`는 상세 페이지에 렌더되지 않는다.** web/에서 이 필드를 쓰는 곳은 검색 일치 문구(`web/lib/matchReason.ts:20`)뿐이다. 2분 안에 읽기에 가장 좋은 필드가 상세에서 빠져 있다. (이 사실은 Codex가 정정해 주어 반영했다.)
- 목차, 접기, 섹션 점프가 없다. 101개 인용 행이 전부 펼쳐져 있다(`web/components/QuoteList.tsx`).

**③ 가독성: 강조가 너무 많아 위계가 없다**
- 상세에서는 항목마다 색 테두리 카드, 화자 표시, 이탤릭 인용이 반복된다(`shots/pc_video_overview.png`). 모든 것이 강조돼 있으니 무엇이 중요한지 구별하기 어렵다.
- 홈 글자 노드의 56%(106/189)가 12px 미만이다. 날짜·칩·"요약" 라벨 같은 보조 정보는 10px로 고정돼 있다(`VideoCard.tsx:16,50,77,96`, `app/page.tsx:101`). 단, 상세 본문은 주로 14px이므로 본문 전체가 작다는 뜻은 아니다(Codex 지적).
- 피드 카드의 칩 "매수 N / 매도 N / 관전 N / 용어 N"은 개수만 보여준다. 이 영상에서 무엇을 얻는지는 알려주지 않는다. 매수·매도는 대부분 비어 있어서(과제 2) 칩은 사실상 "관전 5 · 용어 3" 같은 개수만 남는다.
- 내용 없는 요약도 그대로 노출된다. 홈 첫 줄의 머니코믹스 카드 headline이 "자막 미생성으로 추출 가능 내용 없음"이다(`shots/pc_home_fold.png`). DB에서 같은 패턴은 1건으로 확인했다.

**④ 스크롤 깊이**
- 모바일 홈은 카드 1장에 약 370px(첫 카드 y=1,222부터 문서 끝 8,662까지 20장 평균, 간격 포함 · 16:9 썸네일 전폭)를 쓴다. 한 화면(844px)에 약 2.3장꼴이고, 20장에 10.3화면이다(`shots/mo_home_overview.png`, `shots/mo_channel_fold.png`). 무한 스크롤로 휠 3회 만에 80장까지 쌓인다. 쉽게 지나치고 다시 찾기는 어렵다.
- 상세는 모바일 16.2화면이다. 12분짜리 영상(아래 과제 2 샘플 1) 하나에 항목 48개와 인용 133개가 붙는다.

**⑤ 필터 동선**
- 조작 수단은 검색창 1개와 "쇼츠 숨기기" 토글 1개뿐이다. 채널·기간·주제·종목 필터가 피드에 없다.
- 채널은 별도 페이지로 가야 보이고, 채널 페이지에는 검색이 없다(`web/app/channel/[slug]/page.tsx`. 측정 결과 채널 페이지의 버튼은 쇼츠 토글뿐이다).
- 모바일에서 검색 결과는 채널 그리드 아래에 그려진다. 입력해도 결과가 화면 밖에 있다(`shots/mo_search.png`. 첫 렌더에선 카드 일부가 걸쳐 보였고, 감사 재측정에선 첫 카드 top이 953px로 화면 밖이었다. 첫 화면에 결과가 거의 또는 전혀 안 보인다).
- 검색어가 URL에 저장되지 않는다(`SearchableFeed.tsx`가 useState만 쓴다). 그래서 공유나 뒤로가기로 재진입할 수 없다. 상세의 "← 채널명"은 원래 보던 검색 결과가 아니라 그 채널의 영상 목록(`/channel/<slug>`)으로 간다.

### Codex 제3자 의견 대조
Codex에는 측정 수치와 사실 진술("raw_summary 미렌더", "HEADLINE 반복" 등)을 주었고, 진단 결론과 처방은 주지 않았다(프롬프트 원문 `codex-ux-prompt.txt`). 같은 측정치를 받은 제3자 해석이지, 완전히 독립적인 관찰은 아니다.

| 항목 | 내 진단 | Codex | 판정 |
|---|---|---|---|
| 1순위 문제 | 모바일 첫 화면 요약 0건 | **상세가 결론 전에 근거부터 보여줌**(1순위), 첫 화면은 2순위 | 순위만 다르고 둘 다 지적. 영향 범위는 상세가 더 크다는 Codex 판단에 동의 |
| raw_summary | "렌더 안 됨" | 상세엔 없지만 검색 일치 문구로는 나옴 | **Codex 정정 반영** |
| 12px 미만 56% | 가독성 근거로 사용 | 상세 본문은 14px이니 과대해석 말라 | Codex 지적 반영(보조 정보 한정으로 서술) |
| 필터 동선 | 필터 부재, 모바일 검색 결과가 화면 밖 | 필터 부재, 검색어 URL 미저장, 뒤로가기가 채널로 감 | Codex가 URL·뒤로가기를 추가로 잡음 → 반영 |
| 헤드라인 중복 | 지적 | 지적 | 일치 |
| 처방 | (초안) 스키마 교체를 포함한 전면 재설계 | **화면 재설계가 낫다. 기존 데이터·API는 재사용** | 화면 재설계는 일치. 스키마 교체는 Codex 의견이 아님 |

### 개선안 두 트랙

**(a) 점진 개선** (기존 컴포넌트 유지, 공수 1~2일은 추정)
1. 홈: 채널 그리드를 가로 스크롤 칩 한 줄로 줄이고, 검색창과 피드를 첫 화면으로 올린다.
2. 모바일 카드: 썸네일을 좌측 작은 정사각(약 96px)으로 바꾸는 리스트형으로 전환한다. 한 화면 카드 수가 약 2.3장에서 5장 안팎으로 늘어난다(추정, 미측정).
3. 상세: HEADLINE 박스를 삭제하고, raw_summary를 맨 위에 렌더한다. 썸네일을 축소하고 섹션 순서를 결론, 흐름, 거시, 차트 순으로 바꾼다. 인용은 기본으로 접는다. 빈 섹션은 그리지 않는다(지금도 그리지 않음).
4. 피드 칩을 개수 대신 "핵심 종목 2~3개"로 바꾼다.
5. 검색어를 URL 쿼리로 저장한다.

효과와 한계: 인용 접기만으로 wQwoW_HgNnM 모바일 상세가 16.2화면에서 9.7화면(−40%), PC가 9.8화면에서 7.0화면으로 준다(독립 감사 실측, QuoteList 숨김). 그래도 항목 수(중앙값 40개)는 그대로라 10화면 안팎이 남는다. 홈의 "채널 통계 vs 필터" 구조도 바뀌지 않는다.

**(b) 전면 재설계** (v3 스키마와 함께)
- **홈 = "오늘의 브리핑"**: 상단은 날짜별 tldr 리스트(채널 칩, 한 줄 결론, content_type 배지)다. 상단 필터 바에 채널 다중 선택, 기간, 종목(entities), 유형(시황·인터뷰·교양)을 둔다. 필터 상태는 URL에 저장한다. 채널 통계는 채널 페이지나 푸터로 내린다.
- **상세 = 3층 구조**: ① tldr과 watch_guide(볼지 말지), ② key_points 3~7개와 positions·scenarios, ③ 접힌 근거(quote, numbers, terms)와 chapters(타임스탬프로 YouTube 점프). 썸네일 대신 임베드는 선택 사항으로 둔다.
- **종목 페이지(신규)**: entities 기준으로 "엔비디아를 언급한 최근 영상들의 key_points"를 모아 본다. 지금 검색은 영상 카드를 나열할 뿐이고, 종목 기준으로 주장을 모아 보지 못한다.

**판단: 지금 근거로는 "(b)가 낫다"고 단정할 수 없다. (a)를 먼저 낸다.**
- (a)로도 상세 길이가 40% 준다(실측). 홈 첫 화면 문제도 순서 변경으로 바로 해소된다.
- (b)가 필요해지는 조건은 두 가지다. ① (a) 이후에도 상세가 10화면 안팎으로 남아 사용자 불만이 지속될 때. ② v3 스키마 파일럿이 성공해 `SummaryCard.tsx`(13섹션 하드코딩)를 어차피 새로 써야 할 때. 둘 중 하나라도 해당하면 (b)로 간다. 내 예상은 ②가 성립할 가능성이 높다는 것이지만 아직 검증되지 않았다.
- 사용자 관찰(사용성 테스트) 없이 측정과 코드만으로 낸 판단이다.

### 13섹션 스키마의 구조적 결함
1. **목표가 독자가 아니라 무손실 추출이다.** v2 설계 문서(library `why-summaries-lose-half-the-content`)가 "분량 제한 해제, 모든 항목 quote 필수"를 택했다. 원문 전체가 필요한 독자는 원문을 읽으면 된다. 요약의 일은 고르는 것이다.
   - 현행 가이드(`prompts/summary-guidelines.md:183-192`)에는 분량 기준(10분 2~5천자, 30분 5천~1만자, 2시간 1.5만~2.5만자)과 "같은 내용 중복 항목은 quotes 배열에 합쳐라"가 이미 있다. 그런데 표본 110건 중 약 85건이 이 상한을 넘는다(감사, 영상 길이 구간 근사). iQ2zUAaGoEw(12분)는 상한의 4배다. 즉 **규칙 설계와 함께 규칙 미준수도 원인**이다. 프롬프트 규칙만으로는 안 지켜지니, 저장 단계 기계 검증이 필요하다는 근거가 된다.
2. **섹션 경계가 겹친다.** verdicts, action_items, watchlist는 모두 "조건과 대응"이다. macro_views, data_points, chart_levels는 모두 "숫자"다. 모델이 겹치는 내용을 여러 섹션에 넣는 것은 관찰된 사실이다. 원인이 가이드의 "누락 금지" 강조 때문이라는 것은 추정이다.
3. **채널 성격과 무관한 고정 스키마다.** 교양·숏폼·인터뷰도 주식 라이브용 틀에 맞춘다.
4. **독자의 첫 질문에 답하는 필드가 없다.** "볼 가치가 있나, 어디를 보면 되나"를 다루는 필드가 없다. narrative는 문자열 하나라서 타임스탬프 점프가 안 된다.

### 제안: v3 스키마 (`v3/summary-guidelines-v3.draft.md`)

| v2 (13) | v3 | 이유 |
|---|---|---|
| headline + raw_summary + narrative | `tldr`(1문장) + `chapters`[{ts,title}] | 3중 중복 제거. 흐름은 타임스탬프 목차로 |
| macro_views + watchlist + lessons 일부 | `key_points` 3~7개 (point, detail, ts, quote 1개) | 주장 단위로 통합하고 중요도순 정렬 |
| buys + sells | `positions` (action enum + when: done/today/conditional) | 매매 동사가 quote에 있어야만 허용. 보유·권유·추천 오분류 차단 |
| verdicts + action_items + chart_levels(조건형) | `scenarios` [{if, then, ts}] | 조건과 대응 하나로 |
| data_points + chart_levels(수치형) | `numbers` (최대 8) | key_points와 중복 금지 |
| terms | `terms` (최대 5, 일반 용어 금지) | 유지하되 상한 |
| lessons(rule/counter/reference/analogy) | `takeaways` (rule/counter/reference, 최대 5) | analogy 폐지(실익 낮음) |
| (없음) | `content_type`, `watch_guide`, `entities`, `open_questions` | 유형별 섹션 선택, 볼지 말지, 종목 필터·페이지, 판단 유보 사항 |

핵심 규칙은 다섯 가지다.
- 한 사실은 한 곳에만 쓴다.
- 출력은 transcript의 25% 이하로 한다.
- quote는 항목당 1개, 150자 이내로 한다.
- content_type이 clip(3분 미만)이나 entertainment이면 tldr과 key_points 1~3개만 쓴다.
- chapters의 마지막 ts가 영상 길이의 85% 이후여야 한다(후반부 누락 검출).

검증 가능한 규칙(인용 원문 포함 여부, 길이 비율, 인용 중복, 후반부 커버리지)은 `save_summary.py`에서 기계 검사로 막는 것을 권한다.

### 이행 순서 제안
1. **v3 파일럿**: 운영 요약 파이프라인으로 채널별 2~3편(총 20~30편)을 v3 가이드(`v3/summary-guidelines-v3.draft.md`)로 생성한다. 기존 v2와 나란히 비교해 분량·누락·오류를 잰다. 통과하면 `prompts/summary-guidelines.md`를 교체하고 `save_summary.py`에 v3 검증을 추가한다.
2. 웹 상세는 `schema` 필드로 v2와 v3를 분기 렌더한다. 기존 1,820건은 어댑터로 표시한다(headline → tldr, raw_summary → 맨 위 본문, narrative → chapters 파싱 시도, 나머지는 접힌 "상세 추출" 탭).
3. 재요약은 노출 가치가 높은 범위부터 한다. 예: 경제 채널 요약 범위 30일 이내와 교양 채널 최근분. 전체 재요약 비용은 v3 실제 출력량을 측정한 뒤에 정한다.
4. 웹은 (a)를 먼저 낸다: 홈 순서 변경, HEADLINE 중복 제거, raw_summary 노출, 인용 접기, 검색어 URL 저장. v3 파일럿이 통과하면 상세·홈을 (b)로 재설계한다.
